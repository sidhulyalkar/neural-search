# External-user benchmark

Retrieval evaluation and product adoption answer different questions.

- NDCG/MRR/qrels ask whether judged datasets are ranked well.
- The external-user benchmark asks whether a researcher can actually get from an unfamiliar checkout to a defensible reuse decision.

Neither substitutes for the other.

## Event schema

Usability-study clients can emit JSONL events with:

```json
{
  "session_id": "study_001",
  "timestamp": "2026-08-19T10:00:00-07:00",
  "event_type": "dataset_saved",
  "success": true,
  "dataset_id": "dandi:000001",
  "usefulness": "useful",
  "would_use_for_analysis": "yes",
  "known_before": false,
  "metadata": {}
}
```

Timestamps must be timezone-aware. Events are deliberately small and can be generated by the web app, CLI studies, notebook studies, or scripted onboarding tests.

The API endpoint is local-only application storage, not a hidden analytics beacon:

```text
POST /api/adoption/events
GET  /api/adoption/report
```

By default the event stream is written to `artifacts/frontend/adoption_events.jsonl`. Set `NEURAL_SEARCH_ADOPTION_EVENTS` to isolate a study or test run.

## Recommended event types

- `session_started`
- `search_attempt`
- `search_success`
- `metadata_failure`
- `dataset_saved`
- `notebook_generated`
- `notebook_execution`
- `reuse_decision`
- `workflow_complete`

Additional event types are allowed and retained even when they do not contribute to the current metrics.

## Metrics

The evaluator reports:

- search success rate;
- median and p90 time to first successful search;
- useful-dataset discovery rate per session;
- save rate per session;
- notebook-generation rate per session;
- notebook-execution success rate;
- metadata-failure recovery rate;
- positive reuse-decision rate (`yes` or `maybe`);
- novel-useful discovery rate (`known_before=false` among useful/partially useful outcomes);
- workflow completion rate.

Run locally:

```bash
neural-search adoption report \
  --events artifacts/frontend/adoption_events.jsonl \
  --output reports/adoption/study.json
```

A deterministic fixture is committed at `data/eval/adoption_events_demo.jsonl` so the metric implementation itself is regression-tested in CI.

## Study protocol

A useful external-lab study should recruit multiple researcher roles rather than only project maintainers. Suggested strata:

- experimental neuroscientist;
- computational neuroscientist;
- methods developer;
- data curator/infrastructure researcher;
- graduate student unfamiliar with the repository.

Give participants realistic tasks rather than feature tours. Example tasks:

1. Find a dataset suitable for a stated analysis and explain why it is reusable.
2. Recover after discovering that a desired metadata field is absent.
3. Compare two candidate datasets and make a reuse decision.
4. Generate a starter notebook and attempt to execute the first data-loading cells.
5. Use the reanalysis workbench to identify one feasible extension and explain its assumptions.
6. Identify which system capabilities were unavailable and how that affected confidence.

## Interpretation rules

Do not report adoption metrics as retrieval relevance metrics or scientific correctness.

A high workflow-completion rate can coexist with poor ranking. A high NDCG can coexist with a product researchers cannot operate. A successful notebook launch does not establish that a downstream statistical conclusion is valid.

For serious external validation, pair the event report with:

- canonical retrieval metrics;
- expert review of a sample of dataset reuse decisions;
- notebook execution logs;
- qualitative failure coding;
- participant role/experience metadata;
- the profile reproducibility manifest used during the study.

The long-term target is a coupled evaluation: **retrieval quality × workflow completion × scientific decision quality**.
